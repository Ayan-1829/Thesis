Before we start

Why this matters

Every developer swears by a favourite practice — tests first, pair programming, AI assistants, tabs over spaces. Ask for evidence and the room gets loud.

Software engineering research settles such arguments with tools and data from real projects and real developers. With GitHub and AI coding assistants, there are more open questions than ever.

This chapter introduces SE research: problems, methods, data, metrics, tools and venues.

Part 1 of 12

What software engineering research studies

Software engineering (SE) research studies how software is built, tested, maintained and used by teams — and how to do it better. It mixes tools (program analysis, test generation, AI coding assistants) with empirical studies of real projects and developers.

Methods

Key techniques to know

Static analysis

Inspect code without running it: linters, SonarQube, type checkers, data-flow analysis.

Testing techniques

Unit, integration and mutation testing; coverage; fuzzing; property-based tests.

Repository mining

GitHub API, commit histories, issue trackers; linking commits to bugs (SZZ algorithm).

Software metrics

Size, complexity, churn, coupling — features for prediction.

AI for code

Code LLMs for generation, summarisation, review and repair — and their evaluation.

Qualitative analysis

Coding interview transcripts into themes (thematic analysis).

Thesis ideas

StarterCode-smell study of local projects

Analyse open-source projects by Bangladeshi developers with SonarQube; relate smells to bug fixes.

StandardSecurity of AI-generated code

Generate solutions to tasks with AI assistants and scan them for vulnerabilities; test safer prompting.

StandardGenerated vs human tests

Compare EvoSuite tests with developer tests by mutation score on real projects.

StandardDeveloper practices survey

Survey and interview local developers on testing or code review; thematic analysis.

AmbitiousLLM program repair, verified

Evaluate LLM fixes on Defects4J with manual correctness checks beyond tests.

Thesis ideas

Getting started in four weeks

  1. Week 1read two MSR or ICSE papers close to your interest
  2. Week 2mine one repository with PyDriller; plot commit activity
  3. Week 3run a tool (SonarQube, EvoSuite) on a real project
  4. Week 4define the study design and sample; one-page idea
Pitfalls: biased repository samples (only famous projects), forks and bots in the data, survey questions that lead the answer, trusting tests as proof that AI code is correct.

Worked example 1 of 2

Worked example 1

Design a mining study: “Do projects with continuous integration have fewer bugs?”
Show the solution
Sample: 500 active GitHub Java projects (≥50 stars, ≥2 years of history, no forks), half adopting CI during their life. Measure bug-fix commits per KLOC before and after CI adoption (a before/after design within each project), control for size and activity, and discuss confounders (mature teams adopt CI).

Worked example 2 of 2

Worked example 2

An LLM repairs 40% of Defects4J bugs because the tests now pass. Why is that not the full answer?
Show the solution
Tests are incomplete: a patch can pass them but be wrong (overfitting patches). Manually check a sample of patches for semantic correctness against the developer fix, and report the correct-fix rate separately.

Practice

Practice (1 of 2)

Try each one yourself first, then check the answer.

1. Name four research methods used in SE.
Show the answer
Controlled experiments, mining software repositories, tool building with benchmarks, surveys and interviews, case studies.
2. What is mutation testing?
Show the answer
Seeding small artificial faults (mutants) into code and measuring how many the test suite detects — the mutation score.
3. What is Defects4J used for?
Show the answer
A benchmark of real Java bugs with tests, used for testing, fault localisation and program-repair research.

Summary

Summary

  • SE research studies how software is built, tested and maintained, with tools and empirical evidence.
  • Methods: experiments, repository mining, tool building with benchmarks, surveys/interviews, case studies.
  • Know static analysis, testing (mutation, coverage), metrics, repository mining and AI-for-code evaluation.
  • Select repositories and participants carefully; filter forks, bots and toy projects.
  • Passing tests is not proof of correctness — check AI fixes manually.
  • Venues: ICSE, ESEC/FSE, ASE, ISSTA, MSR, ICSME; journals TSE, TOSEM, EMSE.
